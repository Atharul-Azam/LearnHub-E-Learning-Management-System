# LearnHub – Decisions, Conflicts and Ambiguities

Sources: **SRS** = `E-Learning_Management_System_SRS.docx` (requirement IDs are those of Table V, section 5);
**DD** = `Detailed_Design_Document_Final.docx` (section numbers as in its table of contents; figures as numbered in the document).

Status values: *Resolved* (a documented choice was made) or *Unresolved* (needs a decision from the client/supervisor).

## B. Ambiguities – the documents are silent

| ID | Topic | What the documents say | Decision (smallest consistent implementation) | Status |
|----|-------|------------------------|----------------------------------------------|--------|
| **D-1** | **Resubmission / replacement of a submission** | DD §6.3 / Fig-39: only *Not Submitted → Submitted On Time / Late → Reviewed*. No replace or resubmit transition. SRS 19.2–19.4 describe uploading once. Class diagram shows submissions 0..* per student/assignment but no uniqueness rule. | **One submission per student per assignment; no replacement or resubmission**, before or after the deadline. Enforced in `assignments/services.py` and by DB constraint `unique_submission_per_student`. Late submissions *are* accepted and flagged (DD §6.3). To allow replacement later, change `submit_assignment` only. Final review: consistent with Fig-39 (no resubmit transition) and the UC16 activity diagram (a *failed* upload returns to file selection and creates nothing, so retry after a rejection works; covered by a test). | Resolved – **please confirm with the client** |
| **D-2** | **Editing a review** | DD §6.3: Reviewed after valid marks saved; no outgoing transition. Nothing forbids correcting a mistake. | A teacher may open a Reviewed submission and save again; it stays Reviewed (no state change). | Resolved |
| **D-3** | **Progress percentage** | SRS 20.2: "percentage of the course activities that the student has completed". DD UC15: opening a material updates progress; Fig-19: `Enrollment.progress`. No formula. | Activities = the course's materials + assignments. Completed = materials the student has opened (`MaterialAccess`, one row per student/material) + assignments the student has submitted. `progress = round-half-up(completed / total × 100)`; 0 when the course has no activities. Recomputed from stored rows and cached in `Enrollment.progress`; recalculated when a material/assignment is added or removed, when a material is opened, when a submission is made, and when the progress page is opened. Viewing **or** downloading a material counts as opening it. | Resolved |
| **D-4** | **Deleting a course** | DD Fig-19: Assignment and LearningMaterial are *compositions* of Course; DD §6.4: the owning teacher or an administrator may remove it after confirmation. | Hard delete (state "Removed"). Cascades to its materials, assignments, enrollments, material-access rows and student submissions; stored files are deleted **after the transaction commits** (`core/files.py`). The confirmation page states what will be deleted. | Resolved |
| **D-5** | **Deleting a student** | DD §6.1: accounts can be permanently deleted after confirmation. | Student's own enrollments, material-access rows and submissions are deleted with the account; files cleaned up after commit. | Resolved |
| **D-6** | **Deleting a teacher who owns courses** | Not specified. | **Blocked** with a message ("remove their courses first") – avoids silently destroying other students' academic records. `Course.teacher` is `on_delete=PROTECT` as a second guard. | Resolved |
| **D-7** | **Which states can be removed / activated** | DD §6.1 text: administrator can activate, reject, deactivate; accounts can be deleted after confirmation. Fig-37 was read as: no remove from Pending, no re-activation of Rejected. | Allowed transitions: Pending→Active, Pending→Rejected, Active→Deactivated, Deactivated→Active. Remove allowed from Active, Rejected, Deactivated. A pending teacher must be approved/rejected first. Table in `accounts/services.py` (`ALLOWED_TRANSITIONS`, `REMOVABLE_STATUSES`). | Resolved – **confirmed against Fig-37** in the final review (Pending has no remove; Rejected only → remove; Active ↔ Deactivated; deactivated login blocked per the figure's design-assumption note) |
| D-8 | Administrator accounts | SRS 4.1/4.3 manage *student and teacher* accounts only. | Admins are created with `createsuperuser`; they never appear in, and cannot be changed through, the account-management pages. | Resolved |
| D-9 | Categories | SRS 9.4: category groups/filters courses; DD Fig-19: `category` is a course attribute. No category management function is specified. | Free-text `Course.category` (whitespace-normalised); the browse filter lists the categories of published courses; the course form suggests existing ones. No category admin screen (it would be an unsupported feature). | Resolved |
| D-10 | Allowed file types and sizes | SRS 9.2, 10.3, 19.2, 22.5 say "allowed type and size" without values. | Configurable in `config/settings/base.py` (`UPLOAD_RULES`, env `MAX_*_MB`). Defaults – thumbnail: png/jpg/jpeg/gif/webp ≤ 2 MB; material: pdf/doc/docx/ppt/pptx/xls/xlsx/txt/zip/mp4 ≤ 50 MB; attachment & submission: documents + png/jpg ≤ 20 MB. Real content is checked (`core/validators.py`). | Resolved – values are assumptions |
| D-11 | Password rule | SRS 22.2: ≥ 8 characters, letters and numbers. | Exactly that, via Django validators (min length 8 + custom letters-and-numbers validator). No extra "common password" rule, to stay within the documented requirement. | Resolved |
| D-12 | Registration fields | SRS 1.3: name, e-mail, password. | Exactly those plus the category. No "confirm password" field (not documented). | Resolved |
| D-13 | Inactivity timeout | SRS 21.5: configurable; DD §6.2. | Default 30 minutes, env `SESSION_INACTIVITY_TIMEOUT_SECONDS`. Implemented with `SESSION_COOKIE_AGE` + `SESSION_SAVE_EVERY_REQUEST` (expiry renews on each request). | Resolved |
| D-14 | Access-denied style | SRS 21.2–21.4. | Wrong **role** → HTTP 403. Someone else's object (another teacher's course, another student's submission) → 404, so existence is not disclosed. Student not enrolled in an existing published course → 403. Hidden/removed course → 404 for students. | Resolved |
| D-15 | Assignment visibility | SRS 11.3: published items visible only to enrolled students. | Assignments are published on creation (no draft state – none is documented). Only enrolled students (course published) can open them. | Resolved |
| D-16 | Hidden course and enrolled students | SRS 6.5, DD §6.4: hidden/removed courses are not shown to students. | Enrolled students also lose access to a hidden course's pages and files until it is published again; their enrollment, submissions and marks are kept. | D-17 | Late submissions | DD §6.3. | `late ⇔ server time at submission > deadline`. A submission exactly at the deadline is on time. The flag is stored once (DD 6.3 `markLate()`); a teacher editing the deadline later does not change existing submissions. | Resolved |
| D-18 | Marks | SRS 14.1: within the maximum marks. | Decimal marks with up to 2 decimal places, 0 ≤ marks ≤ max. Maximum marks cannot be lowered below marks already awarded. | Resolved |

## C. Technical decisions (not business requirements)

* Custom user model (`accounts.User`): e-mail is the login name; `is_active` is derived from `status == Active`, so Django's own session loading ends sessions of deactivated users automatically.
* No Django admin site is enabled (the administrator uses the documented admin pages only).
* Media files have **no public URL**. Every file is streamed by a view that checks role, ownership and enrollment (`core/files.py::file_response`), with `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`; only a small allow-list of types is displayed inline, everything else is forced to download.
* Files are stored under server-generated UUID names; the client's filename is kept only as a sanitised display name.
* Tailwind CSS v4 is compiled by `tools/build_css.mjs` using the `tailwindcss` package's compile API; the compiled `static/css/app.css` is committed, so Node is only needed to change styles.
* Confirmation for destructive/decisive actions is a server-rendered page whose POST performs the action (works without JavaScript; the action never runs on GET).
